# Task progress belongs to the owning Bot

The host observes tasks; it does not write progress prose on the Bot's behalf.

- `manage_task report` durably delivers an observation to that task's receipt ledger. `delivered` acknowledges this internal delivery, not publication to the user. Exact retries/fingerprints are idempotent without a time window. Inspect retains the details.
- Agent message completion, todo/permission/lifecycle events and recovery scans produce source-scoped snapshots. Unchanged snapshots do not start inference or emit messages. Timers recover observations and failed inference only; elapsed time never creates a report.
- The owning Bot's configured model compares the actual goal, same-task evidence, recent user conversation and prior public task reports. Ordinary steps and individual code/tests stay internal. A milestone requires a completed user-relevant stage with observed evidence. The Bot generates one or two short plain-language sentences, or chooses silence. No keyword filter or completed-todo count decides significance.
- Completion, failure and necessary user action are explicit inputs to the Bot, not claims of objective acceptance. Existing task-result review still goes through the owning Bot's full receive-result turn. The monitor no longer appends a fixed completion/uncertainty template. Mandatory permission/help cards and their content-free system alerts remain intact, independently of milestone filtering.
- If inference is unavailable, records remain unassessed for retry; there is no raw-Agent or host-template fallback. Details and real failure/action state remain visible in the task UI and inspect. No new provider/account is selected. APIs use their tool-free side call. A native adapter without `modelOnlyChat`, or an adapter-declared unsupported isolation profile, uses the owning Bot's normal protected turn described below. Other failures, user denial, timeout and failed safety checks never trigger a native fallback.
- Before publishing, persist the decision/outbox, recheck ownership and evidence, append with a stable message ID, flush, then acknowledge the outbox. A lost acknowledgment retries the same ID. Different tasks serialize independently. Legacy quiet outboxes are discarded and re-evaluated from retained task records; no executor is restarted.
- OS task-return alerts are requested only after a Bot-generated milestone or task-review summary is saved, honoring foreground/disable/failure/dedupe settings. Their bodies remain content-free for privacy. Failed system permission is not retried automatically.

No source-session change, UI selection, same display name or sibling Agent permits reassignment of a report. User-requested details are answered by the Bot using inspect/context rather than copying an unsolicited executor log.

## Low-interference Agent conversation

The hybrid protocol uses the existing `task-messages` ledger rather than a new database or arbitrary file watcher. At task publication, the executor is asked to report observed outcomes/blockers/proposed adjustments at natural safe points, not every step. These reports do not interrupt the executor or publish to the user. The Bot can analyze a new report immediately and send concrete authorized advice without asking the user.

The host also schedules actual questions to the execution conversation: an initial ten-minute check, then the Bot selects a bounded five-to-thirty-minute cadence appropriate to the work. These are technical conversation intervals, not milestone thresholds. Only running, owned tasks receive periodic inquiries. New blocker reports in help/user/reconnect waits may receive scoped advice, while existing user decisions and approvals remain pending. Approval waits never receive automatic steering; queued/stopped/terminal tasks are excluded from new communication. One unanswered inquiry is retained per task, so no reply does not cause repeated injections. Due reviews can examine an outstanding request without resending it. A long-running tool may not answer until it returns: absence of an answer is not proof of failure. Inspect retains queued/delivered/uncertain and correlated reply state for user-requested detail.

| Existing App/CLI path | Ordinary automatic inquiry | Concrete useful advice |
|---|---|---|
| Codex (active-turn steer exists) | queued at a safe turn boundary; never periodic steer | existing acknowledged `turn/steer`, with uncertain RPC never replayed |
| Kimi and Grok ACP | existing same-session next turn; no App in-turn steering contract | same safe boundary; queued is not reported as delivered |
| Claude, pi, OpenCode, Droid | existing common next-turn delivery; no universal App steer contract | same boundary, preserving adapter session/resume behavior |

Advice and inquiries have stable task-bound request IDs. Routine replies use ordinary assistant text in the same execution conversation; the host links the exact response message IDs. Optional proactive report calls may use `reply:<requestId>`, but an inquiry or acknowledgement does not require an MCP/reporting action. For acknowledged live steering, the App records the active message as a target and associates a response only after that exact turn successfully completes. It updates the response observation time once, without promoting uncertain/queued/cancelled deliveries. The host records transport delivery separately from reply. A reply or a claimed adjustment is not independent evidence of adoption. Instructions explicitly state that Bot suggestions are not user consent and cannot expand approvals, spending, external sending or destructive actions. No automatic task restart is inferred. After restart the ledger remains inspectable, interrupted deliveries are uncertain and are not replayed under new IDs.

The communication design was reviewed using an internal decision-review service with synthetic technical input. Live service evidence remains provider-specific: prior Kimi/Codex real-service validation is retained; local synthetic provider/transport tests do not certify every CLI's runtime communication or semantic quality.

For CLIs that request an explicit MCP approval even for `manage_task`, the host preserves that approval. Routine progress does not require this extra call: the preferred record is the Agent's existing persisted conversation, with `report` optional under current permissions. Safe-boundary deliveries record the exact assistant response message IDs, so a normal reply can be correlated even when a CLI has no report tool. The host does not bypass a CLI's explicit permission request to make progress logging appear automatic.

## Evidence and runtime limits

`manage_task inspect` adds top-level `executionEvidence` after its existing task/source ownership check. It projects the same executor's recent native and application tool receipts: tool kind, target path, explicit completion/failure state, and whether output exists. It never returns native file/code/output bodies. An assistant's claim remains distinct from an actual tool receipt; malformed or incomplete receipts stay unconfirmed. Paths are redacted and output is bounded. This does not provide arbitrary source-code access or sibling task access.

Actual validation used a Codex owning Bot and a Kimi execution Agent in one persisted execution conversation. The Bot chose a direction, continued that Agent, inspected two real Read receipts, and recorded the scoped assessment. An earlier blocked assessment is preserved, and the follow-up did not repeat the Reads. That validates the ordinary result/continuation path; it is **not** evidence that real periodic tool-free inference passed for every backend.

Historical controlled-inference tests (`realCLI=false`) and real result-review tests remain distinct from native periodic-judgment evidence. Consult the task's versioned acceptance report for the actual provider, role and package tested; a real owning Bot with a controlled execution worker is not a two-real-CLI test. Grok has not received a real quota request.

## Protected native judgment

Native judgment reserves the normal owning source conversation only while it is idle, with no queued/paused human input. It validates task ownership, Bot membership, current model and permission settings. The ordinary native launch authorization and explicit adapter permission callbacks remain active. Never allow, deny and ask policies are not overridden; a refusal is persisted and is not repeatedly solicited on each new report. Unconfirmed permission likewise waits for an explicit permission-settings change. `manage_task inspect` exposes the bounded `automaticJudgment` state so unavailable/denied inference is not mistaken for delivery. A denied Bot may still answer ordinary user queries through its usual permissions.

Each consideration has a one-use native conversation key, the normal identity/mode/permission policy and its current observation envelope. Its temporary App tool catalog is empty and its required MCP gateway grants no App tools or computer capability, so execution/delegation/review-tool instructions do not conflict with internal consideration. Normal user and real executor turns retain their catalogs and gateway. The supported-CLI gateway requirement is unchanged: a missing gateway still fails closed. It uses the same existing Bot backend/model/identity, not copied credentials or an unprotected print subprocess. Private drafts stay internal and are excluded from subsequent human model history. Only actual public conversation and persisted published reports mean that the user has been told; a discarded proposal must never suppress an eventual milestone. Native bindings for the one-use key are discarded after gateway detach; ordinary human thread bindings remain intact.

As defense against stale or stray calls, the narrower application invocation guard permits only existing ACL-controlled `manage_task list/match` and exact-task `inspect`. `match` is recognized for later integration, not added to this candidate's schema. `message/stop/resume/report/prioritize/describe`, delegation, file and execution tools are rejected regardless of tool-level `mutating:false`. Explicit native tool approval requests during judgment are rejected; existing permission/help cards remain visible. Ordinary native CLI implicit capabilities still fall under the existing **whole native-turn local execution authorization**; this path is not a claim that every CLI's implicit native tool is forcibly disabled. Automatic suggestions are delivered separately through the original task channel only after checking the owning Bot's actual task-management permission.

Durable consideration receipts cache the same input/owner/configuration, serialize concurrent requests, defer to human input and retain retry/denial states. An interrupted prepared consideration becomes uncertain instead of blindly replaying. Native failures use a technical backoff; that never decides whether progress is significant. Publication rechecks actual source context and evidence; stale private proposals are discarded. Outgoing transport state and correlated replies are separate observations, so queued/delivering cannot be promoted to received or adopted just to make a test pass.


Publication and coordination now use one canonical task observation envelope and share the same in-flight owning-Bot judgment. Consuming a report is bookkeeping, not a second semantic question. Outgoing transport remains visible to the Bot but is not new executor progress; actual incoming replies, execution evidence and lifecycle/ownership still change the observation. This prevents the host's own inquiry/advice from generating another progress judgment or invalidating an otherwise valid milestone. A corrupt communication ledger still blocks sending, while a separately observed failure can be summarized. Native setup, capability probing and cleanup have one bounded budget; the one-use client is stopped before its gateway is detached. Human input retains priority.

The user-facing text field is an ordinary short app status. Internal rationale, formats and receipt mechanics belong in evidence/coordination, not the unsolicited user summary. This is generated by the owning Bot in context, not a keyword filter or fixed sentence. Real-service samples and their wording are retained in the continuation evidence; they do not guarantee every model response style.


The permanent source-chat input for a new consideration is a small internal boundary marker. The full current envelope lives only in the temporary scope for that model request; the per-task input fingerprint/decision and original source/executor records retain its basis. No user or historical messages are deleted. Windowing excludes internal records before applying public-message limits/counts, so long silent monitoring cannot evict the real chat or fill a pane with invisible rows.


Automatic communication is a separate mutating `manage_task message` action, irrespective of its tool-wide `mutating:false` declaration. `coordinationPermission` runs the existing ordinary deny/ask/semantic/approval gate with the full call, after enabled-tool and scoped identity/mode checks. Auto-run standing authorization adds no new prompt. Checking/crash and rejection/timeout receipts are held by exact task/owner/permission revision, rather than retried on a new report; final observation/source freshness is checked again. `inspect.automaticCommunication` exposes this distinction from `automaticJudgment`. No planner/schema policy or ordinary native MCP refusal is waived.

The protected observation envelope includes bounded same-executor execution metadata already persisted by the host (kind/target/explicit state/output presence and length), never arbitrary code/file bodies. It helps the owning Bot assess an execution claim without reading source. Agent assertions, transport receipts and these tool observations still do not by themselves establish the whole user objective.

Private internal entries are excluded before transcript/pane window limits and counts; actual user messages, public tools/status/errors/approval content remain. New internal considerations persist only a short boundary marker in the source chat; the full current prompt is supplied from temporary trusted scope, and old task/history evidence is retained.
